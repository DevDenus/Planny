# Решения и отличия от ТЗ

Исходный документ: «Универсальный планировщик. MVP», версия 0.1 от 4 ноября 2026 года. Решения ниже имеют приоритет над ним.

## Что изменилось по сравнению с ТЗ

| Тема | Было в ТЗ | Решение | Почему |
|---|---|---|---|
| Приглашения | Статусы pending, accepted, declined, список входящих | Приглашений нет. Участник сразу получает событие в календарь и уведомление | В семье подтверждение только мешает |
| Права на событие | Менять может только организатор | Все участники равноправны: меняют событие и состав участников, могут удалить его у всех | Внутри семьи это удобнее |
| Занятость | Только по явному разрешению, с отзывом | Видна всем пользователям, но только как интервалы «занят» | Событие можно поставить кому угодно, поэтому занятость полезно видеть сразу. Детали остаются закрытыми |
| Push-уведомления | Если поддерживает браузер | Вне MVP. Уведомления только внутри сайта | При закрытом сайте пользователь увидит уведомление при следующем входе, этого достаточно |
| Администрирование | Admin API с отдельным портом и ключом | Только CLI на сервере. Сетевых админ-маршрутов нет | Самая чувствительная часть системы не слушает ни один порт |
| Сессии | Сессия в BFF, короткоживущий токен к backend | Сессиями владеет backend. Токен непрозрачный, BFF хранит его в зашифрованной cookie | Взлом BFF не позволяет выпускать токены для произвольных пользователей, а отзыв срабатывает сразу |
| Синхронизация | Периодический запрос изменений | Опрос счётчиков версий через `GET /sync` | Не нужен журнал изменений с его проблемами порядка транзакций |
| Сервисные аккаунты | Ключ сервисного аккаунта либо пользователя | Ключ всегда принадлежит пользователю | Один путь проверки прав. Сервисные аккаунты решим в проекте интеграции |
| Архивация карточек | Отдельный статус архивации | Только мягкое удаление | Одно состояние вместо двух |
| Настройки уведомлений | Раздел в настройках | Перенесены на v1.1 | Сам ТЗ относит точные параметры уведомлений к v1.1 |
| Нагрузочные тесты | Проверка p95 под нагрузкой | Не проводим | Нагрузка от одной семьи ничтожна |
| Kanban | После MVP, в MVP только список | В MVP: Kanban, свои колонки, drag-and-drop карточек и колонок, метки, комментарии, история карточек, календарь как вид доски | Kanban нужен сразу, а модель данных к нему уже готова |
| Навигация | «Списки» и «Доски» отдельно, возможно объединение | Один раздел «Доски», список и Kanban стали видами доски | Это одни и те же данные, ТЗ допускало такое объединение |

## Что добавлено к ТЗ

- **Личная доска по умолчанию.** Создаётся вместе с пользователем, её нельзя архивировать. Быстрая задача попадает туда без выбора доски. На неё можно добавить других участников, но её создатель всегда остаётся владельцем: иначе задачам без `board_id` некуда было бы попасть.
- **Создатель события тоже участник.** Все запросы календаря идут через одну таблицу участников, а `created_by` остаётся справочным полем.
- **Категория и напоминание личные.** У каждого участника свой цвет и свой срок напоминания.
- **История связи с событием.** Запись `event_linked` видна только участникам события. Журнал задачи читают все участники доски, а событие личное, поэтому записи фильтруются при чтении, а данные в журнале остаются полными. Тот же фильтр действует на страницы истории и на `last_change` в конфликте версий.
- **Занятость при редактировании.** `GET /availability` принимает `exclude_event_id`, иначе редактируемое событие конфликтовало бы само с собой.
- **Бесконечные серии.** Серия либо бесконечна, либо ограничена датой или числом повторов.
- **Scopes не закрывали всех маршрутов.** Чтение категорий относится к `events:read`, потому что без него нельзя понять поле события. `GET /me` и `GET /users` доступны любому ключу. Поиску и связям задачи с событием нужны scopes обеих сторон. Отметка уведомлений прочитанными осталась за сессией: `notifications:read` даёт только чтение, а интеграция не должна гасить уведомления вместо человека.
- **Scope закрывает данные, а не только маршрут.** Без него ключ не увидит чужую сторону связи даже внутри разрешённого ответа: иначе `events:read` читал бы названия задач через `linked_tasks`.
- **Записи без чтения не бывает.** `keys create` не выдаёт `events:write` и `tasks:write` без `events:read` и `tasks:read`. Ответ на запись и конфликт версий содержат объект целиком, так что ключ только на запись обещал бы ограничение, которого нет. Настоящий ключ только на запись потребовал бы урезанных ответов на всех записывающих маршрутах, а Аде он не нужен.
- **Ключ не проходит смену пароля.** Одноразовый пароль касается человека на сайте. Сброс пароля оператором не должен останавливать интеграцию, а для её остановки есть отзыв ключа и блокировка.
- **Пропуск коротких месяцев.** Серия «каждый месяц 31-го» просто пропускает месяцы без такого числа.
- **События на весь день не считаются занятостью.** Иначе день рождения закрывал бы весь день. При необходимости позже появится флаг.
- **Видимость задач в календаре.** Задача видна её исполнителям. Задача без исполнителя видна всем участникам доски. Владелец доски и создатель карточки особых прав здесь не имеют.
- **Уведомление о сроке.** Получают исполнители, а у карточки без исполнителя владельцы доски. Иначе по задачам на личной доске срок не напоминался бы никому.
- **Вид «Календарь» на доске.** Показывает все задачи доски со сроком независимо от исполнителя, потому что это обзор доски, а не личный календарь. Фильтры доски сужают его так же, как другие виды.
- **Колонки и метки.** Ими управляют editor и owner.
- **Комментарии.** Пишут editor и owner, viewer только читает. Автор меняет и удаляет свой комментарий, owner может удалить любой.
- **Перенос между досками.** Выполняется той же операцией `move`. Метки сбрасываются, а исполнители, которых нет на новой доске, снимаются.
- **Границы истории.** Перестановки внутри колонки не записываются, иначе журнал тонул бы в шуме.
- **Удаление карточки с подтверждением.** Интерфейса восстановления нет, а на телефоне кнопка стоит рядом с «Сохранить».
- **Перенос без уведомления.** Он виден на доске и в истории, а уведомления о каждом переносе были бы шумом.
- **Напоминание о прошедшем моменте не срабатывает.** Если до начала уже меньше заданного времени, разовое событие остаётся без напоминания, а у серии сработает следующий повтор. Иначе сохранение формы давало бы уведомление сразу же.
- **Срок объявляется только будущий.** Карточка с уже прошедшим сроком уведомления не даёт, а карточка со сроком на сегодня даёт, даже если 09:00 уже прошло.
- **Изменение задачи — это название, срок и приоритет.** Описание и дата начала исполнителей не тревожат.
- **Срок считается прошедшим по зоне того, кто его задал.** Если дата уже прошла у автора, но ещё не у исполнителя в другой зоне, уведомления о сроке не будет. Считать это отдельно для каждого получателя в одной семье не окупается.
- **Смена зоны серии — это изменение времени.** Участники получают `event_updated`: от зоны зависит, на какие дни падают повторы. У разового события моменты не меняются, поэтому уведомления нет.
- **Повтор серии не длиннее 366 дней.** Разовое событие может длиться сколько угодно.
- **Напоминания одной серии независимы.** В непрочитанных остаётся последнее уведомление каждого из них, поэтому при нескольких напоминаниях на событие непрочитанных может быть несколько. В форме напоминание одно, там это всегда одно уведомление.

## Закрытые вопросы из ТЗ

| Вопрос | Ответ |
|---|---|
| Публичный веб-хост | Домашний сервер со статическим IP и доменом `planny.roflix.site`, Caddy в отдельном стеке |
| Сколько пользователей | Одна семья, но технических ограничений на число аккаунтов нет |
| Повторения | Базовые серии. Исключения и правка одного экземпляра в v1.1 |
| Браузерные уведомления | Только уведомления внутри сайта |
| Админ-процесс | CLI на сервере, админ-панели нет |

## Технические решения

| Решение | Почему |
|---|---|
| Backend — модульный монолит на FastAPI | Один разработчик, одна база, понятные границы модулей без накладных расходов на сервисы |
| BFF — отдельный тонкий прокси на Python, без Next.js | SSR закрытому приложению не нужен, а серверные маршруты провоцируют переносить туда логику |
| Фоновая работа только на PostgreSQL | Redis и Celery на таком масштабе не окупаются |
| Время в UTC, отдельной логики под перевод часов нет | Перевода часов нет, а хранение в UTC просто и однозначно. Единственная поправка в развёртке серий: она выбирает повторы по реальным моментам, поэтому в зонах с переводом повтор в этот час не теряется |
| Серии считаются в местном времени события | Иначе месячная серия ломается для времени, где местная дата отличается от даты UTC. Проверено на `rrule` |
| Отметка `due_notified_at` на карточке | Защита от дублей через `dedupe_key` живёт, пока живёт уведомление, а прочитанные удаляются через 90 дней |
| Даты без времени хранятся типом `date` | Иначе «весь день» уезжает на соседний день у пользователя с другой зоной |
| Серии хранятся как RRULE и разворачиваются при чтении | Бесконечную серию нельзя материализовать, а RRULE расширяется в v1.1 без миграции данных |
| OpenAPI генерируется из кода, снимок лежит в репозитории | Вручную вести YAML дороже, чем контролировать расхождения в CI |
| Месяц, неделя и день на FullCalendar | Ядро под MIT, пересечения и многодневные события уже решены |
| FullCalendar получает стенное время профиля и работает в `UTC` | Часовой пояс задан в профиле и может отличаться от пояса браузера. Сетка не видит настоящих моментов и не пересчитывает их сама |
| FullCalendar 7, тема `classic` с палитрой из токенов приложения | В версии 7 сетки входят в `@fullcalendar/react`, а цвета темы задаются CSS-переменными |
| Drag-and-drop на dnd-kit: датчики мыши и касаний, слой под указателем, автопрокрутка | Эти части решены и проверены. Сортировка из коробки перемещает карточки между колонками прямо во время перетаскивания, а нам нужна неподвижная доска с линией вставки |
| Место вставки считается по положению элементов на странице в момент проверки | Геометрия всегда та, что видит пользователь, в том числе во время автопрокрутки, а сами расчёты лежат в чистых функциях |
| Перенос с клавиатуры написан отдельно от датчика dnd-kit | Датчик двигает координаты, а по стрелкам нужно идти по местам между карточками. Состояние и линия вставки общие с мышью |
| Перенос на другую доску, снявший метки или исполнителей, увеличивает `version` | Иначе форма, открытая раньше, вернёт снятое обратно или получит ошибку про чужую метку |
| Удаление метки пишет `unlabeled` в историю карточек | Карточка изменилась, и история должна это показать, как при удалении участника с доски |
| Порядок карточек: дробные ключи и блокировка строки колонки | Перенос меняет одну строку. Без блокировки одновременные переносы дают одинаковые ключи, и следующая вставка падает. Проверено на прототипе |
| История пишется в транзакции изменения | Журнал не расходится с данными, очередь не нужна |
| До этапа 8 миграции не писались, источник схемы — модели. С этапа 8 схема меняется только миграциями | Пока данных, которые надо переносить, не было ни у кого, проверка миграций только отнимала время. Перед выходом на сервер схема собрана в одну начальную миграцию, а `alembic check` в CI следит, чтобы модели и миграции не расходились. Миграции идут только вперёд: откат — это восстановление копии |
| Исключения попадают в лог типом и стеком, без сообщения | Сообщение может цитировать данные пользователя, как ошибка базы цитирует значение из нарушенного ограничения. Цена — чуть больше работы при разборе сбоя |
| Перенос карточки принимает правки в том же запросе | Иначе правка успевает уйти в уведомлении тому, кто на новую доску не попадёт, а при сбое карточка сохраняется частично. Две операции одной транзакцией проще, чем отдельный маршрут |
| Обновление — образы собираются на dev-машине, едут на сервер через `scp` и `docker load`, версия равна тегу образа, git в установке не участвует. Откат через копию | Серверу не нужен доступ к приватному репозиторию и сборка Node. Собирается рабочая копия как есть: что работает на сервере и что попадёт в репозиторий, решается независимо. Ревизия git и время сборки записываются только для справки, а номер версии должен расти, иначе `docker load` затёр бы образы, к которым нужно откатываться. Реестр образов и деплой из CI для одной машины не окупаются. Откат восстановлением проверяется `make restore-check`, а `downgrade` остался бы непроверенным путём |
| Caddy — отдельный стек, BFF входит в его внешнюю сеть Docker `edge` и не публикует порт на хосте | Caddy обслуживает и другие сайты, поэтому ему не место в стеке Planny. Порт на хосте не нужен, а BFF доступен только по имени `planny-bff` из сети `edge` |
| Копии на `/mnt/hdd2` с проверкой точки монтирования, пробное восстановление раз в неделю по таймерам systemd | Без проверки `mkdir` на размонтированном диске заполнил бы системный. `backup.sh` проверяет лишь оглавление архива, поэтому настоящую гарантию даёт только регулярное восстановление во временный проект |
| Выдача сессии и смена учётных данных идут через блокировку строки `app_user` | Иначе вход со старым паролем, начатый до сброса, создаёт сессию уже после закрытия всех сессий. Счётчик версий пароля и уровень `SERIALIZABLE` здесь не нужны |
| Восстановление разворачивает копию в отдельную базу и только потом подменяет текущую | `pg_restore --list` читает лишь оглавление и пропускает обрезанный файл. Проверено на копии без последних 128 байт |
| Отдельных макетов нет, стиль референсов общий для всех экранов | Стиль уже понятен, а экраны без референса строятся из тех же компонентов |
| Разработка и проверка на dev-машине, выход на сервер последним этапом | Промежуточные версии в сеть не выкладываем. Локальный Compose повторяет схему сервера, чтобы снизить риск на последнем этапе |
