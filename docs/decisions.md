# Решения и отличия от ТЗ

Исходный документ: «Универсальный планировщик. MVP», версия 0.1 от 4 ноября 2026 года. Решения ниже имеют приоритет над ним.

## Что изменилось по сравнению с ТЗ

| Тема | Было в ТЗ | Решение | Почему |
|---|---|---|---|
| Приглашения | Статусы pending, accepted, declined, список входящих | Приглашений нет. Участник сразу получает событие в календарь и уведомление | В семье подтверждение только мешает |
| Права на событие | Менять может только организатор | Все участники равноправны: меняют событие и состав участников, могут удалить его у всех | Внутри семьи это удобнее |
| Занятость | Только по явному разрешению, с отзывом | Видна всем пользователям, но только как интервалы «занят» | Событие можно поставить кому угодно, поэтому занятость полезно видеть сразу. Детали остаются закрытыми |
| Push-уведомления | Если поддерживает браузер | Вне MVP. Уведомления только внутри сайта | При закрытом сайте пользователь увидит уведомление при следующем входе, этого достаточно |
| Администрирование | Admin API с отдельным портом и ключом | Только CLI на сервере. Сетевых админ-маршрутов нет | Самая чувствительная часть системы не слушает ни один порт |
| Сессии | Сессия в BFF, короткоживущий токен к backend | Сессиями владеет backend. Токен непрозрачный, BFF хранит его в зашифрованной cookie | Взлом BFF не позволяет выпускать токены для произвольных пользователей, а отзыв срабатывает сразу |
| Синхронизация | Периодический запрос изменений | Опрос счётчиков версий через `GET /sync` | Не нужен журнал изменений с его проблемами порядка транзакций |
| Сервисные аккаунты | Ключ сервисного аккаунта либо пользователя | Ключ всегда принадлежит пользователю | Один путь проверки прав. Сервисные аккаунты решим в проекте интеграции |
| Архивация карточек | Отдельный статус архивации | Только мягкое удаление | Одно состояние вместо двух |
| Настройки уведомлений | Раздел в настройках | Перенесены на v1.1 | Сам ТЗ относит точные параметры уведомлений к v1.1 |
| Нагрузочные тесты | Проверка p95 под нагрузкой | Не проводим | Нагрузка от одной семьи ничтожна |
| Kanban | После MVP, в MVP только список | В MVP: Kanban, свои колонки, drag-and-drop карточек и колонок, метки, комментарии, история карточек, календарь как вид доски | Kanban нужен сразу, а модель данных к нему уже готова |
| Навигация | «Списки» и «Доски» отдельно, возможно объединение | Один раздел «Доски», список и Kanban стали видами доски | Это одни и те же данные, ТЗ допускало такое объединение |

## Что добавлено к ТЗ

- **Личная доска по умолчанию.** Создаётся вместе с пользователем, её нельзя архивировать. Быстрая задача попадает туда без выбора доски. На неё можно добавить других участников, но её создатель всегда остаётся владельцем: иначе задачам без `board_id` некуда было бы попасть.
- **Создатель события тоже участник.** Все запросы календаря идут через одну таблицу участников, а `created_by` остаётся справочным полем.
- **Категория и напоминание личные.** У каждого участника свой цвет и свой срок напоминания.
- **Бесконечные серии.** Серия либо бесконечна, либо ограничена датой или числом повторов.
- **Пропуск коротких месяцев.** Серия «каждый месяц 31-го» просто пропускает месяцы без такого числа.
- **События на весь день не считаются занятостью.** Иначе день рождения закрывал бы весь день. При необходимости позже появится флаг.
- **Видимость задач в календаре.** Задача видна её исполнителям. Задача без исполнителя видна всем участникам доски. Владелец доски и создатель карточки особых прав здесь не имеют.
- **Уведомление о сроке.** Получают исполнители, а у карточки без исполнителя владельцы доски. Иначе по задачам на личной доске срок не напоминался бы никому.
- **Вид «Календарь» на доске.** Показывает все задачи доски со сроком независимо от исполнителя, потому что это обзор доски, а не личный календарь.
- **Колонки и метки.** Ими управляют editor и owner.
- **Комментарии.** Пишут editor и owner, viewer только читает. Автор меняет и удаляет свой комментарий, owner может удалить любой.
- **Перенос между досками.** Выполняется той же операцией `move`. Метки сбрасываются, а исполнители, которых нет на новой доске, снимаются.
- **Границы истории.** Перестановки внутри колонки не записываются, иначе журнал тонул бы в шуме.
- **Удаление карточки с подтверждением.** Интерфейса восстановления нет, а на телефоне кнопка стоит рядом с «Сохранить».
- **Перенос без уведомления.** Он виден на доске и в истории, а уведомления о каждом переносе были бы шумом.

## Закрытые вопросы из ТЗ

| Вопрос | Ответ |
|---|---|
| Публичный веб-хост | Домашний сервер со статическим IP и доменом, существующий Caddy |
| Сколько пользователей | Одна семья, но технических ограничений на число аккаунтов нет |
| Повторения | Базовые серии. Исключения и правка одного экземпляра в v1.1 |
| Браузерные уведомления | Только уведомления внутри сайта |
| Админ-процесс | CLI на сервере, админ-панели нет |

## Технические решения

| Решение | Почему |
|---|---|
| Backend — модульный монолит на FastAPI | Один разработчик, одна база, понятные границы модулей без накладных расходов на сервисы |
| BFF — отдельный тонкий прокси на Python, без Next.js | SSR закрытому приложению не нужен, а серверные маршруты провоцируют переносить туда логику |
| Фоновая работа только на PostgreSQL | Redis и Celery на таком масштабе не окупаются |
| Время в UTC, код под перевод часов не пишем | Перевода часов нет, а хранение в UTC просто и однозначно |
| Серии считаются в местном времени события | Иначе месячная серия ломается для времени, где местная дата отличается от даты UTC. Проверено на `rrule` |
| Даты без времени хранятся типом `date` | Иначе «весь день» уезжает на соседний день у пользователя с другой зоной |
| Серии хранятся как RRULE и разворачиваются при чтении | Бесконечную серию нельзя материализовать, а RRULE расширяется в v1.1 без миграции данных |
| OpenAPI генерируется из кода, снимок лежит в репозитории | Вручную вести YAML дороже, чем контролировать расхождения в CI |
| Месяц, неделя и день на FullCalendar | Ядро под MIT, пересечения и многодневные события уже решены |
| Drag-and-drop на dnd-kit | Сортировка, касания и управление с клавиатуры уже решены |
| Порядок карточек: дробные ключи и блокировка строки колонки | Перенос меняет одну строку. Без блокировки одновременные переносы дают одинаковые ключи, и следующая вставка падает. Проверено на прототипе |
| История пишется в транзакции изменения | Журнал не расходится с данными, очередь не нужна |
| Выдача сессии и смена учётных данных идут через блокировку строки `app_user` | Иначе вход со старым паролем, начатый до сброса, создаёт сессию уже после закрытия всех сессий. Счётчик версий пароля и уровень `SERIALIZABLE` здесь не нужны |
| Восстановление разворачивает копию в отдельную базу и только потом подменяет текущую | `pg_restore --list` читает лишь оглавление и пропускает обрезанный файл. Проверено на копии без последних 128 байт |
| Отдельных макетов нет, стиль референсов общий для всех экранов | Стиль уже понятен, а экраны без референса строятся из тех же компонентов |
| Разработка и проверка на dev-машине, выход на сервер последним этапом | Промежуточные версии в сеть не выкладываем. Локальный Compose повторяет схему сервера, чтобы снизить риск на последнем этапе |
