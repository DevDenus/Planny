# Выход на сервер

Пошаговая инструкция для первой установки, обновлений и проверок этапа 8. Порядок работы скриптов описан в шапке `deploy/server/update.sh`, копии и восстановление — в [deploy/backup/README.md](../deploy/backup/README.md), объёмы на диске — в [operations.md](operations.md).

Версия — это тройка чисел вида `0.1.0`. Образы собираются на dev-машине и приезжают на сервер одним файлом. Репозиторий на сервер не клонируется, Node и сборка там не нужны.

Git в установке не участвует. `make release` собирает рабочую копию как есть, закоммичена она или нет, и ничего не проверяет в репозитории: ни чистоту дерева, ни теги. На сервере работает то, что собрано, а в репозиторий попадает то, что вы решите зафиксировать. Эти решения независимы.

Номер версии должен расти с каждым комплектом, который вы ставите на сервер. Подойдёт любой номер: пока пробуете, берите `0.0.1`, `0.0.2` и так далее, а `0.1.0` пусть будет первой версией, которой пользуется семья. Скрипту важно только, чтобы номер вырос. Он откажется ставить версию ниже установленной и такую же: `docker load` заменил бы образы текущей версии, и откату было бы не к чему вернуться.

Какому коду соответствует версия на сервере, видно в файлах `REVISION` (sha коммита, с суффиксом `-dirty`, если были незафиксированные изменения, или `unknown` без git) и `BUILT_AT` (время сборки по UTC) в `/opt/planny/releases/<версия>/`. Те же значения записаны в метках образов:

```bash
docker image inspect -f '{{json .Config.Labels}}' planny-backend:0.1.0
```

Это справочные сведения, на работу они не влияют.

## Что нужно заранее

- Сервер на Ubuntu с Docker Engine и плагином compose не старше 2.24: `docker compose version`.
- Та же архитектура процессора, что и у dev-машины (x86_64). Образы собираются на dev-машине, а `update.sh` откажется ставить образ другой архитектуры.
- Постоянный адрес сервера в локальной сети (`LAN_IP`) и статический публичный IP.
- A-запись `planny.roflix.site` указывает прямо на домашний IP, без CDN.
- Роутер пробрасывает на сервер только порты 80 и 443. Порты 8000, 8080 и 5432 наружу не пробрасываются.
- Второй диск смонтирован в `/mnt/hdd2`, папка для копий `/mnt/hdd2/planny-backups` создаётся скриптом сама.
- Доступ по ssh с dev-машины и `sudo` на сервере.

## Caddy

Caddy живёт в отдельном стеке в репозитории PunkyServer, папка `caddy/`, на сервере `/opt/caddy`. Он проксирует `planny.roflix.site` на `planny-bff:8080` с HSTS `max-age=31536000` без `includeSubDomains`, а `cloud.roflix.site` на `nextcloud-app:80`. Сертификаты Caddy сам выпускает и продлевает через Let's Encrypt и хранит в `/opt/caddy/caddy_data`.

С Planny Caddy соединяет внешняя сеть Docker `edge`: BFF входит в неё под именем `planny-bff` и не публикует порт на хосте. Сеть создаётся один раз командой `docker network create edge`. Её создаёт либо перенос Caddy, либо `update.sh`, смотря что запустится раньше.

Порядок переноса Caddy описан в `caddy/README.md` репозитория PunkyServer, здесь он не дублируется. Сначала перенесите Caddy, потом устанавливайте Planny: до этого сайт отвечает ошибкой 502.

## Первая установка

На dev-машине, в корне репозитория:

```bash
make release VERSION=0.1.0
```

Команда собирает оба образа из текущей рабочей копии и пакует `dist/planny-0.1.0.tar`. Файлы `VERSION`, `REVISION` и `BUILT_AT` лежат в комплекте.

```bash
scp dist/planny-0.1.0.tar punkyserver:/tmp/
```

На сервере распакуйте комплект и запустите скрипт:

```bash
tar -xf /tmp/planny-0.1.0.tar -C /tmp
```

```bash
sudo /tmp/planny-0.1.0/deploy/server/update.sh
```

Первый запуск завершается кодом 2: скрипт создал `/opt/planny/.env` со свежими случайными секретами и правами 600. Дальше:

1. Откройте файл: `sudo nano /opt/planny/.env`.
2. Впишите в `LAN_IP` адрес сервера в локальной сети. Скрипт проверит, что он назначен интерфейсу сервера.
3. Проверьте `BACKUP_DIR=/mnt/hdd2/planny-backups` и `BACKUP_MOUNT=/mnt/hdd2`.
4. `PLANNY_VERSION` не трогайте, его пишет скрипт. `COOKIE_SECURE` и `TRUST_FORWARDED_FOR` на сервере должны остаться `true`.

Файл `.env` скрипт никогда не перезаписывает. Сохраните его копию отдельно: в резервную копию базы он не входит.

Запустите скрипт ещё раз и ответьте `y` на вопрос. Флаг `--yes` вопрос пропускает.

```bash
sudo /tmp/planny-0.1.0/deploy/server/update.sh
```

Успех выглядит так: в конце строки `==> Готово`, `Версия: 0.1.0 (до этого: не было)` и таблица `docker compose ps`, где `db`, `api`, `worker` и `bff` в состоянии `running` или `healthy`, а `migrate` завершился. На первой установке копия перед обновлением не снимается: базы ещё нет.

Проверьте, что таймеры резервных копий установились:

```bash
systemctl list-timers 'planny-*'
```

В списке должны быть `planny-backup.timer` (каждый день в 03:30) и `planny-trial-restore.timer` (по воскресеньям в 04:30). Затем откройте <https://planny.roflix.site>: должен появиться экран входа. Распакованный комплект в `/tmp` можно удалить, рабочая копия лежит в `/opt/planny/releases/0.1.0`.

### Что лежит на сервере

| Путь | Что это |
|---|---|
| `/opt/planny/.env` | Секреты и `PLANNY_VERSION`, права 600 |
| `/opt/planny/releases/<версия>/` | Комплект без образов. `deploy/.env` в нём — ссылка на общий `.env` |
| `/opt/planny/current` | Ссылка на запущенную версию |
| `/opt/planny/logs/` | По одному журналу на запуск `update.sh` |
| `/mnt/hdd2/planny-backups/` | Резервные копии |

Скрипт хранит три последние версии и ту, что работала до обновления. Остальные папки и образы он удаляет.

## Аккаунты семьи

Регистрации нет, аккаунты создаёт оператор на сервере. Команды в `docker compose exec` запускаются из папки `deploy` текущей версии: ссылка `.env` в ней нужна Compose.

```bash
cd /opt/planny/current/deploy
```

```bash
sudo docker compose -f compose.yaml -f compose.prod.yaml exec api planny users create sasha --name "Саша"
```

Команда печатает одноразовый пароль. Передайте его человеку лично. При первом входе сайт требует сменить пароль: пока он не сменён, остальные маршруты отвечают `403 password_change_required`. Остальные команды описаны в [api.md](api.md#6-cli).

```bash
sudo docker compose -f compose.yaml -f compose.prod.yaml exec api planny users list
```

Потеряли пароль: `planny users reset-password <логин>` выдаёт новый одноразовый пароль.

## Обновление

Тот же путь, что и при первой установке, только с новой версией, большей установленной. `.env` уже есть, поэтому запуск не прерывается.

```bash
make release VERSION=0.1.1
```

```bash
scp dist/planny-0.1.1.tar punkyserver:/tmp/
```

```bash
tar -xf /tmp/planny-0.1.1.tar -C /tmp
```

```bash
sudo /tmp/planny-0.1.1/deploy/server/update.sh
```

Скрипт делает по порядку:

1. Проверяет комплект (`SHA256SUMS`), версию compose, `.env` (все переменные из нового `.env.example` на месте, `LAN_IP` назначен серверу) и что версия выше установленной.
2. Загружает образы через `docker load` и сверяет их архитектуру с сервером. Создаёт сеть `edge`, если её нет.
3. Раскладывает комплект в `releases/<версия>` и подтягивает образ `db`.
4. Снимает копию базы через `backup.sh` на второй диск. Если копия не снялась, обновление не начинается и ничего не меняется.
5. Останавливает `api`, `worker` и `bff`. База продолжает работать.
6. Переключает `current` и `PLANNY_VERSION` на новую версию и запускает всё: сначала `migrate` выполняет `alembic upgrade head`, затем стартуют сервисы. Простой меньше минуты.
7. Обновляет юниты и таймеры systemd, удаляет старые версии.

### Откат

Если новая версия не поднялась, скрипт возвращает прежнюю: восстанавливает копию из шага 4 через `restore.sh` и запускает старые образы. Данные, внесённые между копией и сбоем, теряются. Окно равно времени самого обновления. Если сбой случился до остановки сервисов, база не менялась и копия не нужна. На первой установке откатываться некуда: исправьте причину и запустите скрипт снова.

Понизить версию нельзя, и поставить ту же версию тоже: скрипт откажется. Откат на более старую версию — это восстановление копии, см. [Резервные копии](#резервные-копии).

Флаг `--reinstall` разрешает поставить ту же версию поверх себя, например когда сборка с этим номером не удалась до запуска:

```bash
sudo /tmp/planny-0.1.1/deploy/server/update.sh --reinstall
```

Осторожно: образы этой версии заменяются, поэтому при сбое переустановки скрипт восстановит базу из копии, но образы останутся новыми, прежних уже нет. Обычно проще собрать комплект со следующим номером.

### Коды выхода

| Код | Что значит |
|---|---|
| 0 | Версия установлена и запущена |
| 1 | Сбой, откат выполнен или ничего не менялось. Отказ ответить `y` на вопрос тоже даёт 1, как и отказ ставить версию ниже или равную установленной |
| 2 | `.env` только что создан или в нём ошибка: заполните его и запустите снова |
| 3 | Откат не удался. Скрипт печатает копию перед обновлением и команду для ручного восстановления |

Журнал каждого запуска лежит в `/opt/planny/logs/update-<версия>-<время>.log`, его путь скрипт печатает первой строкой и в конце.

## Резервные копии

Копии по расписанию, второй диск и проверка `BACKUP_MOUNT` описаны в [deploy/backup/README.md](../deploy/backup/README.md). Здесь только команды для ручного запуска на сервере.

Копия прямо сейчас:

```bash
sudo systemctl start planny-backup.service
```

Пробное восстановление самой свежей копии прямо сейчас. Команда ждёт окончания и возвращает код выхода службы:

```bash
sudo systemctl start planny-trial-restore.service
```

```bash
journalctl -u planny-trial-restore -e
```

Полное восстановление на живую базу. Скрипт останавливает `api`, `worker` и `bff`, подменяет базу и запускает их снова:

```bash
ls -t /mnt/hdd2/planny-backups
```

```bash
sudo env PLANNY_ENV=prod /opt/planny/current/deploy/backup/restore.sh /mnt/hdd2/planny-backups/planny-ГГГГММДД-ЧЧММСС.dump
```

Скрипт покажет число пользователей в копии и попросит ввести `restore`.

Упавший запуск таймера виден в `systemctl --failed`. Проверяйте этот список после каждого воскресенья: другого уведомления нет.

## Проверки этапа 8

### AC-01: сайт снаружи, закрытые порты

1. С телефона на мобильной сети, не на Wi-Fi дома, откройте <https://planny.roflix.site>. Войдите и поработайте с календарём: создайте событие, обновите страницу, событие на месте.
2. Узнайте публичный IP на сервере:

```bash
curl -4 ifconfig.me
```

3. С ноутбука, подключённого к точке доступа телефона (не к домашней сети), просканируйте порты:

```bash
nmap -Pn -p 1-65535 <публичный IP>
```

Полное сканирование идёт долго. Короткий вариант:

```bash
nmap -Pn -p 80,443,8000,8080,5432 <публичный IP>
```

Ожидается: открыты только 80 и 443, остальные `closed` или `filtered`. Вместо nmap подойдёт онлайн-сканер портов.

4. Заголовок HSTS:

```bash
curl -I https://planny.roflix.site
```

Ожидается ответ 200 и строка `strict-transport-security: max-age=31536000` без `includeSubDomains`.

5. С того же внешнего устройства API не отвечает:

```bash
curl -m 10 http://<публичный IP>:8000/api/v1/health
```

Ожидается таймаут или отказ в соединении. Проверять публичный IP изнутри домашней сети нельзя: роутер может вернуть пакеты внутрь.

### AC-02: API из LAN

С другого устройства в локальной сети, не с сервера. Без авторизации API отвечает `401`:

```bash
curl -i "http://<LAN_IP>:8000/api/v1/events?from=2026-11-01T00:00:00Z&to=2026-12-01T00:00:00Z"
```

Ожидается `HTTP/1.1 401` и код `unauthorized`.

Теперь ключ только на чтение. На сервере, в папке `/opt/planny/current/deploy`:

```bash
sudo docker compose -f compose.yaml -f compose.prod.yaml exec api planny keys create --user sasha --name "scope-check" --scopes events:read,tasks:read
```

Команда один раз печатает секрет вида `pln_<prefix>_<secret>`. На проверяющем устройстве положите его в переменную и убедитесь, что чтение работает:

```bash
KEY='pln_...'
```

```bash
curl -i -H "Authorization: Bearer $KEY" "http://<LAN_IP>:8000/api/v1/events?from=2026-11-01T00:00:00Z&to=2026-12-01T00:00:00Z"
```

Ожидается `200`. Запись событий и задач ключу недоступна:

```bash
curl -i -X POST -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"title":"Не должно создаться"}' http://<LAN_IP>:8000/api/v1/events
```

```bash
curl -i -X POST -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"title":"Не должно создаться"}' http://<LAN_IP>:8000/api/v1/tasks
```

Ожидается `403` с кодом `insufficient_scope` и `events:write` (`tasks:write`) в `details.required`. После проверки отзовите ключ:

```bash
sudo docker compose -f compose.yaml -f compose.prod.yaml exec api planny keys list --user sasha
```

```bash
sudo docker compose -f compose.yaml -f compose.prod.yaml exec api planny keys revoke <id>
```

Запрос с отозванным ключом получает `401`.

### AC-11: восстановление на сервере

Пробное восстановление вручную, как описано выше:

```bash
sudo systemctl start planny-trial-restore.service
```

```bash
journalctl -u planny-trial-restore -e
```

Ожидается код выхода 0 и строки с файлом копии, числом пользователей и ревизией Alembic. Затем полное восстановление по процедуре из раздела [Резервные копии](#резервные-копии): `restore.sh` на настоящей копии. После него сверьте список пользователей командой `planny users list` и войдите на сайт под одним из них со старым паролем. Сначала снимите копию (`sudo systemctl start planny-backup.service`): после первой установки её ещё нет, а данные, внесённые после копии, восстановление заменит.

### AC-13: перетаскивание на телефонах

На настоящих телефонах и на компьютере откройте доску в виде Kanban и проверьте:

1. Долгое нажатие берёт карточку, палец переносит её в другую колонку, линия вставки показывает место.
2. Карточка остаётся на новом месте после перезагрузки страницы.
3. На втором устройстве под другим пользователем перенос появляется в пределах 10 секунд.
4. На компьютере мышью работает так же.
5. С клавиатуры: пробел берёт карточку, стрелки двигают её, пробел отпускает, Esc отменяет.

### p95 обычных операций

С другого устройства в LAN, не с сервера. Скрипт лежит в репозитории, на устройстве нужен только Python 3.10 или новее. Создайте отдельный аккаунт для замера и войдите под ним на сайте, чтобы сменить одноразовый пароль:

```bash
sudo docker compose -f compose.yaml -f compose.prod.yaml exec api planny users create p95-check --name "Замер"
```

```bash
python3 deploy/tools/measure_p95.py --url https://planny.roflix.site --login p95-check
```

Пароль берётся из `PLANNY_PASSWORD` или запрашивается. Скрипт создаёт свою доску, события и задачи и удаляет их в конце (доска остаётся в архиве). Код выхода 0 означает p95 меньше 500 мс, 1 — больше, 2 — ошибка. Аккаунт после замера можно заблокировать: `planny users block p95-check`.

### Сертификаты Caddy

```bash
sudo docker logs caddy 2>&1 | grep -iE "certificate obtained|renew"
```

Ожидается строка `certificate obtained successfully` для `planny.roflix.site`. Продление Caddy делает сам за несколько недель до окончания срока.

## Если что-то пошло не так

- **Логи сервисов** (из `/opt/planny/current/deploy`):

```bash
sudo docker compose -f compose.yaml -f compose.prod.yaml logs --tail 100 migrate api bff worker
```

- **Журнал обновления** лежит в `/opt/planny/logs/`, самый свежий файл `update-*.log`.
- **Caddy отвечает 502.** BFF не запущен или не подключён к сети `edge`. Проверьте, что `planny-bff` есть среди контейнеров сети:

```bash
docker network inspect edge
```

- **Службы systemd.** Упавшая копия или пробное восстановление видны здесь, причина в `journalctl -u planny-backup -e`:

```bash
systemctl --failed
```

- **Копия не снимается.** Проверьте, что `/mnt/hdd2` смонтирован: `mountpoint /mnt/hdd2`. Иначе `backup.sh` отказывается писать, чтобы не заполнить системный диск.
- **Откат не удался (код 3).** Следуйте командам из вывода скрипта: в них указана копия перед обновлением и точный вызов `restore.sh`.
