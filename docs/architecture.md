# Архитектура

## 1. Обзор

Всё работает на одном домашнем сервере в Docker Compose. Публично доступен только сайт через существующий Caddy. API слушает локальную сеть, база доступна только контейнерам, а административные операции выполняются через CLI на сервере.

```
Интернет ──443──> Caddy (уже есть) ──> BFF + SPA ──┐
                                                   ▼
Ада и другие ──LAN-IP:порт + ключ──────────> Backend API ──> PostgreSQL
                                                                 ▲
Оператор ──docker compose exec──> CLI ───────────────────────────┤
Worker ──────────────────────────────────────────────────────────┘
```

Главный принцип: бизнес-логика, проверки прав и валидация живут в сервисах backend. API, CLI и worker вызывают одни и те же сервисы, а BFF логики не содержит.

| Компонент | Задача | Откуда доступен |
|---|---|---|
| Caddy | Домен и TLS | Из интернета, порт 443 |
| BFF | Отдаёт SPA, держит cookie, проверяет CSRF, ограничивает частоту входа, проксирует разрешённые маршруты | Только от Caddy |
| Backend API | Бизнес-логика, права, контракт OpenAPI | Из внутренней сети Docker и с LAN-IP |
| Worker | Напоминания, сроки задач, очистка | Портов нет |
| CLI | Операции оператора | Через `docker compose exec` на сервере |
| PostgreSQL | Данные | Только из внутренней сети Docker |

API, worker и CLI используют один образ и отличаются командой запуска.

## 2. Сеть

Ниже схема сервера. Разработка идёт на dev-машине, отличия описаны в разделе [Окружения](#окружения).

```yaml
services:
  bff:
    ports:
      - "127.0.0.1:8080:8080"   # сюда проксирует Caddy
    networks: [public, backend]
  api:
    ports:
      - "${LAN_IP}:8000:8000"   # порт только на LAN-адресе
    networks: [lan, backend]
  worker:
    networks: [backend]
  db:
    networks: [backend]

networks:
  public: {}
  lan: {}
  backend:
    internal: true
```

- **Порт API публикуется только на конкретном LAN-IP.** Docker добавляет правила iptables в обход ufw, поэтому запись `8000:8000` откроет порт на всех интерфейсах, включая внешний.
- **У API есть отдельная сеть `lan`.** Порт контейнера, подключённого только к сети с `internal: true`, опубликовать нельзя.
- **Caddy проксирует домен только на BFF.** Если он работает в Docker, BFF подключается к его сети, и порт на `127.0.0.1` не нужен.
- **Роутер пробрасывает только порты Caddy.**
- **Закрытость проверяется снаружи.** Сканирование портов с внешнего адреса входит в проверку AC-01.

### Окружения

Всё разрабатывается и проверяется на dev-машине. На сервер приложение выходит один раз, последним этапом, поэтому Caddy и настоящая сеть в разработке не участвуют.

| | Dev-машина | Сервер |
|---|---|---|
| Когда | Все этапы до последнего | Только последний этап |
| Вход браузера | `http://localhost`, BFF на `127.0.0.1` | Домен через Caddy, HTTPS |
| API снаружи контейнеров | Только `127.0.0.1` | LAN-IP |
| Cookie сессии | `planny_session`, без `Secure` | `__Host-planny_session`, с `Secure` |
| Резервные копии | На локальный диск | По расписанию на другой диск |

Общая часть лежит в `deploy/compose.yaml`: сервисы и сети, включая `backend` с `internal: true`. Файлы `compose.dev.yaml` и `compose.prod.yaml` добавляют только публикацию портов. Поэтому BFF, прокси на API, CSRF и изоляция базы проверяются в разработке так же, как будут работать на сервере.

Настройки cookie различаются, потому что браузеры по-разному обращаются с `Secure` на `localhost`. Код один, значения приходят из окружения.

Только на сервере можно проверить подключение к Caddy, реальный IP клиента в лимите входа, HTTPS с настоящими флагами cookie и закрытость портов снаружи.

## 3. Авторизация

Все запросы к API идут с заголовком `Authorization: Bearer`. Backend ищет хеш токена в БД и собирает объект `Principal`: пользователь, тип доступа и scopes. Сессия и ключ различаются только источником, дальше путь проверки один.

Токены непрозрачные, JWT и refresh-токенов нет. AC-07 всё равно требует проверки по БД на каждый запрос, а один индексированный запрос ничего не стоит. Блокировка пользователя и отзыв ключа срабатывают мгновенно.

### 3.1 Вход на сайт

1. Браузер отправляет логин и пароль на `POST /bff/login`.
2. BFF применяет лимит по IP и вызывает `POST /api/v1/auth/login`, передавая общий секрет и реальный IP клиента.
3. Backend проверяет лимит по паре логин и IP, затем пароль в Argon2id, создаёт запись `session` и возвращает токен.
4. BFF шифрует токен, кладёт его в cookie `__Host-planny_session` с флагами `Secure`, `HttpOnly`, `SameSite=Strict` и выдаёт CSRF-токен в отдельной cookie `__Host-planny_csrf`, которую читает SPA.
5. На каждом следующем запросе BFF расшифровывает cookie, для изменяющих методов сверяет CSRF-токен из заголовка `X-CSRF-Token` и вызывает backend с `Authorization: Bearer <токен>`.

CSRF-токен — это HMAC от токена сессии. Хранить его не нужно, поэтому он переживает перезапуск BFF. У самого `POST /bff/login` сессии ещё нет, его защищает требование `Content-Type: application/json`: чужая страница не может отправить такой запрос без preflight, а на него BFF не отвечает.

BFF не хранит состояния, поэтому его перезапуск не разлогинивает пользователей. Он не может получить токен пользователя без пароля. При взломе BFF под угрозой только активные сессии, а не все аккаунты.

`POST /api/v1/auth/login` принимается только с общим секретом BFF в заголовке `X-BFF-Secret`, реальный IP клиента приходит в `X-Client-IP`. Подбирать пароли напрямую из LAN нельзя.

Сессия живёт 30 дней и продлевается при использовании. У cookie срок фиксированный, поэтому BFF перевыпускает её раз в сутки, иначе активного пользователя выбросило бы через 30 дней. Смена пароля закрывает остальные сессии пользователя, блокировка закрывает все сессии и отзывает ключи.

Argon2id считается без блокировки, поэтому за это время пароль могли сменить, а пользователя заблокировать. Перед созданием сессии вход блокирует строку `app_user` и сверяет, что хеш пароля и статус остались прежними. Смена пароля, сброс, блокировка и разблокировка берут ту же блокировку. Такой порядок гарантирует, что закрытие сессий не пропустит сессию, создаваемую в этот момент.

### 3.2 Лимит входа

Лимит стоит до проверки пароля, потому что Argon2id намеренно дорогой. Жёсткой блокировки аккаунта нет: иначе любой знающий логин мог бы заблокировать члена семьи из интернета. Вместо этого растущая пауза для пары логин и IP: первые четыре ошибки бесплатны, с пятой пауза начинается с минуты и удваивается до часа. Ошибки старше суток забываются, успешный вход сбрасывает счётчик.

Внешний слой стоит в BFF: не больше 20 попыток с одного IP за 5 минут. Этот счётчик живёт в памяти, потому что при перезапуске он только забывает недавние попытки.

### 3.3 Ключи интеграций

- Формат `pln_<prefix>_<secret>`, в базе хранятся `prefix` и SHA-256 от секрета. Секрет имеет высокую энтропию, поэтому Argon2id здесь не нужен.
- Срока действия может не быть, но ключ всегда отзывается вручную.
- Ключ принадлежит пользователю и не может обойти его права.
- Ключу недоступны `/auth/*` и изменение профиля.
- Выпуск и отзыв только через CLI.
- Маршрут закрыт для ключей, пока сам не объявит scopes. Зависимости `PendingSession` и `CurrentSession` пускают только сессию, а ключ проходит только через `require_scopes`. Новый маршрут без объявленных scopes не расширяет доступ ключа, а таблица в `tests/test_api_keys.py` не даст забыть его классифицировать.
- Scope закрывает и данные другой стороны связи. Сервис собирает ответ по `principal.allows(...)`, поэтому `linked_tasks`, `linked_events`, сроки в календаре и записи о связи в истории задачи видит только ключ с нужным scope.
- Записи о связи отсеиваются в самом запросе к журналу, а не после него, для участника доски вне события так же, как для ключа. Поэтому страница, курсор и `last_change` в конфликте строятся только из видимых записей.
- Scope записи выдаётся только вместе со scope чтения той же области. Запись и конфликт версий отвечают объектом целиком, поэтому ключа, который пишет и не читает, на деле не существует.
- Одноразовый пароль ключ не останавливает. `must_change_password` относится к человеку на сайте, а ключ выдан оператором и от пароля не зависит, поэтому сброс пароля не роняет интеграцию.
- Блокировка пользователя отзывает его ключи, разблокировка их не возвращает. Выпуск ключа берёт блокировку той же строки `app_user`, что и блокировка пользователя, поэтому отзыв не пропустит ключ, создаваемый в этот момент.
- `last_used_at` пишется не чаще раза в минуту, как и отметка использования сессии.

### 3.4 CLI

CLI работает внутри контейнера и напрямую вызывает сервисы backend. Первый вход делается через одноразовый пароль, который CLI выводит в терминал, а флаг `must_change_password` заставляет сменить его. Все действия пишутся в `audit_log`. Команды перечислены в [api.md](api.md#6-cli).

## 4. Backend

Модульный монолит с модулями `identity`, `calendar`, `tasks` и `notifications`.

Слои: роутер проверяет форму запроса, сервис выполняет бизнес-правила и проверяет права, репозиторий работает с БД. Сервисы принимают `Principal` первым аргументом, поэтому права проверяются одинаково из любого входа. Команды CLI вместо него принимают `Operator`: это отдельный тип, поэтому операторскую функцию нельзя вызвать из маршрута по ошибке. Роутеры не содержат логики, сервисы не знают про HTTP.

Транзакцию завершает сервис, а не зависимость FastAPI: код после `yield` выполняется уже после отправки ответа, и клиент получил бы успех при упавшем `COMMIT`.

Модули общаются через публичные функции сервисов и не читают чужие таблицы напрямую. Например, календарь получает сроки задач через сервис `tasks`.

## 5. Время

- Моменты времени хранятся как `timestamptz` и возвращаются в UTC.
- Клиент показывает их в часовом поясе из профиля пользователя.
- Отдельной логики под перевод часов нет: у нас его нет. Там, где он есть, час перевода учитывает `zoneinfo`, а развёртка серий выбирает повторы по реальным моментам, потому что местное время вокруг перевода идёт не по порядку.
- Даты без времени хранятся типом `date` и не конвертируются. Это события на весь день и дедлайны без времени.
- «Сегодня» и «просрочено» считаются по часовому поясу пользователя.

## 6. Серии

### 6.1 Хранение

Повторы в базе не лежат, потому что бесконечную серию нельзя материализовать. Событие хранит первый экземпляр, правило и зону:

| Поле | Значение |
|---|---|
| `start_at`, `end_at` | Первый экземпляр в UTC |
| `start_date`, `end_date` | То же для события на весь день, `end_date` включительно |
| `timezone` | IANA-зона, в которой создано событие |
| `recurrence_rule` | RRULE, у разового события `NULL` |
| `series_end_at` | Конец последнего экземпляра, у бесконечной серии `NULL` |

Примеры правил:

| Серия | `recurrence_rule` |
|---|---|
| Каждый месяц без конца | `FREQ=MONTHLY` |
| Каждый месяц до конца 2027 года | `FREQ=MONTHLY;UNTIL=20271231T235959` |
| Каждую неделю, 4 раза | `FREQ=WEEKLY;COUNT=4` |

`UNTIL` записывается в местном времени без суффикса `Z`, потому что разворачиваем мы тоже в местном времени. `dateutil` отвергает сочетание местного начала и `UNTIL` в UTC с ошибкой `ValueError`.

API принимает простой объект `{freq, until, count}`, а RRULE собирает сервер. Поэтому клиенты не могут записать произвольное правило.

### 6.2 Развёртка

Серия считается в местном времени события. Иначе событие «1-го числа в 01:00 по Москве» в UTC становится «каждое 31-е в 22:00», и в 2027 году теряются март, май, июль, октябрь и декабрь.

Код проверен на прототипе: ограничение датой и числом, бесконечная серия, короткие месяцы, экземпляр на границе окна.

```python
def to_local(instant, tz):
    return instant.astimezone(tz).replace(tzinfo=None)

def to_utc(local, tz):
    return local.replace(tzinfo=tz).astimezone(UTC)

def parse(rule, start_at, tz):
    return rrulestr(rule, dtstart=to_local(start_at, tz))

CLOCK_MARGIN = timedelta(days=1)

def expand(start_at, end_at, tz_name, rule, window_start, window_end):
    tz = ZoneInfo(tz_name)
    duration = end_at - start_at
    lo = to_local(window_start - duration, tz) - CLOCK_MARGIN
    hi = to_local(window_end, tz) + CLOCK_MARGIN
    starts = (to_utc(s, tz) for s in parse(rule, start_at, tz).between(lo, hi, inc=True))
    return [(s, s + duration) for s in starts if s < window_end and s + duration > window_start]
```

Выборка за период идёт в два шага: SQL отбирает события пользователя, пересекающие окно по `series_end_at`, затем Python разворачивает только запрошенный диапазон. Окно ограничено 366 днями. Чтение отступает назад на длину повтора, поэтому один повтор тоже не длиннее 366 дней: опечатка в годе иначе сломала бы календарь всем участникам.

`rrule` идёт от первой даты, поэтому ежедневная серия в далёком году потребовала бы миллион шагов. Для дневных и недельных серий без `COUNT` начало сдвигается вперёд на целое число шагов, но не дальше `UNTIL`. Месячные серии дают двенадцать шагов в год, а `COUNT` ограничен тысячей, им сдвиг не нужен.

У экземпляра нет своей строки в БД, его идентификатор — пара `(event_id, occurrence_start)`. На неё опираются напоминания и будущие исключения из v1.1.

## 7. Уведомления и напоминания

Уведомления о действиях пользователей пишутся в той же транзакции, что и изменение. Очередь не нужна, потому что внешней доставки нет. Если появится push, он станет отдельным отправителем, читающим таблицу `notification`.

Worker раз в 30 секунд выполняет три задачи:

1. **Напоминания.** Берёт строки `reminder` с `next_fire_at <= now()` через `FOR UPDATE SKIP LOCKED`, создаёт уведомление и считает следующее срабатывание. Для серии это следующий экземпляр после текущего момента, для разового события `NULL`.
2. **Сроки задач.** Создаёт уведомление в день дедлайна в 09:00 по часовому поясу получателя или в момент `due_at`. Получатели — исполнители, а у карточки без исполнителя владельцы доски. Карточка, у которой срок объявлен всем получателям, получает отметку `due_notified_at` и больше не проверяется. Срок, уже прошедший в момент записи, не объявляется: фраза «Сегодня срок» была бы неправдой. Дата считается не прошедшей до конца своего дня.
3. **Очистка.** Удаляет истёкшие сессии и старые прочитанные уведомления.

Защита от дублей — уникальный `dedupe_key` в `notification`, например `reminder:<id>:<occurrence_start>`. После простоя worker выполняет всё пропущенное один раз, а экземпляры серии, пропущенные целиком, не накапливаются. У каждого напоминания серии в непрочитанных остаётся только последнее уведомление.

Пропущенный при простое повтор серии даёт одно уведомление о последнем из наступивших. Предыдущие непрочитанные уведомления этого напоминания отмечаются прочитанными. Напоминания одной серии гасятся независимо: «за день» о завтрашнем повторе и «в начале» о сегодняшнем приходят в один момент, и одно не делает другое устаревшим. Каждое напоминание и каждая карточка обрабатываются в своей транзакции, поэтому сломанная строка не задерживает остальные.

При изменении времени или правила события сервис пересчитывает `next_fire_at` всех его напоминаний.

Момент уже позади не срабатывает: у разового события `next_fire_at` становится `NULL`, у серии берётся следующий повтор. Событие на весь день начинается в полночь в зоне события. Напоминание о задаче не срабатывает, если карточка выполнена или удалена либо получатель больше не на доске.

## 8. Синхронизация

У каждого пользователя есть счётчики версий по областям: `calendar`, `tasks`, `notifications`. Операция в своей транзакции увеличивает счётчики всех затронутых пользователей.

Клиент опрашивает `GET /sync` раз в 5 секунд, пока вкладка видима, и сразу при возврате на неё. Если счётчик вырос, клиент инвалидирует соответствующие запросы TanStack Query.

Этот подход не требует журнала изменений и не теряет данные: обновление строки счётчика упорядочивает конкурентные транзакции, а клиент всегда сравнивает последнее значение. Цена — перечитывание текущего экрана целиком, что на таком масштабе незаметно.

Правила:

- Счётчики обновляются в порядке `user_id`, чтобы избежать взаимных блокировок.
- Изменение задачи увеличивает счётчик `tasks`, а клиент при этом инвалидирует и календарь, потому что в нём показаны сроки.
- Колонки, метки, комментарии и история относятся к области `tasks`.
- Во время перетаскивания клиент откладывает применение обновлений до отпускания карточки.
- `last_seen_at` сессии и `last_used_at` ключа пишутся не чаще раза в минуту, иначе опрос порождал бы постоянные записи.

Если понадобится меньшая задержка, те же счётчики можно отдавать через SSE.

## 9. Одновременные изменения и Kanban

### 9.1 Версии и повторы

- **Версия.** У события, задачи и доски есть поле `version`. `PATCH` передаёт его в теле, при расхождении сервер отвечает `409 version_conflict` и возвращает текущее состояние.
- **Повторы запросов.** `POST` на создание принимает UUID от клиента, повтор с тем же `id` возвращает уже созданный объект. Повторный `DELETE` отвечает `204`. Это защищает от дублей при повторных отправках, в том числе от голосового клиента.

### 9.2 Перенос карточки

`position` — строковый ключ дробной индексации, поэтому перенос меняет одну строку, а остальные карточки не трогаются. Поле использует `COLLATE "C"`: ключи содержат буквы разного регистра, и при локальной сортировке PostgreSQL порядок ломается. Ключ `Zz` должен стоять перед `a0`.

Перенос — отдельная операция `POST /tasks/{id}/move`. Клиент передаёт `after_id`, а позицию считает сервер:

1. Заблокировать строку целевой колонки через `SELECT ... FOR UPDATE`.
2. Найти позицию карточки `after_id` и следующей за ней. Если `after_id` в колонке уже нет, карточка встаёт в конец.
3. Сгенерировать ключ между двумя позициями.
4. Обновить `column_id`, `position` и `completed_at`.
5. Записать историю, если изменилась колонка, и увеличить счётчики.

Блокировка обязательна. Без неё два одновременных переноса в один промежуток получают одинаковый ключ, а следующая вставка между ними падает с ошибкой. Это проверено на прототипе, как и стабильность порядка после 3000 случайных переносов.

Страховка — частичный уникальный индекс `(column_id, position)` только для неудалённых карточек. Полный индекс нельзя: ключ удалённой карточки выдаётся повторно.

Перенос не проверяет и не меняет `version`, поэтому он не конфликтует с правкой названия. Если одну карточку переносят одновременно, побеждает последний перенос. Исключение одно: перенос на другую доску, снявший метки или исполнителей, увеличивает `version`, потому что меняет поля, которые хранит открытая форма.

### 9.3 Колонки

- Завершённость определяется колонкой: перенос в колонку с `is_done` ставит `completed_at`, перенос из неё очищает.
- `complete` переносит карточку в начало первой завершающей колонки, `reopen` в конец первой незавершающей. Если пока операция ждала блокировку, карточку унесли на другую доску, операция начинается заново: права и колонка зависят от доски.
- Смена `is_done` у колонки в одной транзакции обновляет `completed_at` всех её карточек и пишет историю.
- Удаление колонки требует целевую колонку. В неё переносятся все карточки, включая мягко удалённые, потому что на колонку ссылается внешний ключ.
- На доске всегда остаётся хотя бы одна завершающая и одна незавершающая колонка.
- При переносе на другую доску пользователь должен быть editor или owner на обеих. Метки сбрасываются, а исполнители, которых нет на новой доске, снимаются.
- Порядок блокировок: доска, колонка, карточка. Перенос карточки строку доски не трогает, а создание, перенос, смена признака и удаление колонки сначала блокируют доску, поэтому структура одной доски меняется по очереди, а правило о двух видах колонок проверяется точно. Страховка от одинаковых ключей — уникальность `(board_id, position)`. Удаление колонки блокирует целевую колонку раньше карточек, иначе оно взаимно блокируется с переносом.
- Метки на карточке читаются с `FOR KEY SHARE`. Удаление метки берёт `FOR UPDATE`, поэтому либо дожидается записи связи и удаляет её, либо запись видит, что метки уже нет, и отвечает ошибкой поля.

### 9.4 История карточек

Сервис `tasks` пишет `task_activity` в той же транзакции, что и изменение, поэтому журнал не расходится с данными.

- Одна операция даёт одну запись, даже если изменилось несколько полей.
- Названия колонок, меток и досок и значения полей сохраняются снимком. Старые записи не портятся после переименования или удаления.
- Описание записывается только как факт изменения, чтобы журнал не хранил копии текстов.
- Перестановки внутри колонки не записываются.
- Комментарии хранятся отдельно и в историю не попадают.

## 10. Занятость

1. Взять события со временем, в которых участвует пользователь.
2. Развернуть серии в запрошенном окне.
3. Склеить пересекающиеся и соседние интервалы.
4. Вернуть только `start_at` и `end_at`.

## 13. Эксплуатация

- **Секреты** лежат в `.env` на сервере и не попадают в репозиторий и клиентский бандл: пароль БД, общий секрет BFF, ключ шифрования cookie.
- **Миграции** запускаются отдельным одноразовым сервисом Compose перед стартом API. До этапа 8 вместо миграций сервис `migrate` запускает `python -m app.schema`.
- **Логи** структурированные, `X-Request-ID` проходит от BFF к backend.
- **Резервные копии.** Ежедневный `pg_dump` хранится минимум 14 дней и уезжает на другой диск, потому что всё работает на одной машине. Процедура восстановления описана в `deploy/backup/` и проверяется на чистой базе.
- **Здоровье.** `GET /health` без авторизации нужен для проверок Compose.

## 14. Тестирование

- **Unit:** серии, склейка занятости, расчёт позиций, правила прав.
- **Integration:** CRUD на настоящем PostgreSQL. Матрица прав проверяет каждый маршрут для каждой роли и отсутствие доступа без токена. Параллельные переносы в одно место колонки проверяют блокировку.
- **BFF:** CSRF, cookie, закрытые маршруты, лимит входа.
- **E2E:** основные сценарии в Playwright для настольного и мобильного размера, включая перетаскивание карточек. `make e2e` поднимает отдельный проект Compose со своей базой и портом и удаляет его после прогона, поэтому данные стека разработки не страдают.
- **Сеть:** сканирование портов снаружи по критерию AC-01 при выходе на сервер.
