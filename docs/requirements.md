# Требования к продукту

## 1. Цель и рамки

Planny — закрытый планировщик для одной семьи. Каждый пользователь ведёт личный календарь, а совместная работа идёт через совместные события, общие доски и назначение задач.

Основной клиент — адаптивный сайт для компьютера и мобильного браузера. Нативных приложений в MVP нет. Вся логика и данные находятся в независимом backend, которым могут пользоваться локальные клиенты через API.

Термины:

- **Событие** — запись в календаре с интервалом времени и участниками.
- **Задача** — карточка с исполнителями, сроками и приоритетом.
- **Доска** — контейнер задач с колонками-статусами.
- **Список, Kanban и календарь** — три представления задач одной доски.
- **BFF** — серверная прослойка сайта, которая общается с закрытым API.

## 2. Роли

| Роль | Возможности |
|---|---|
| Оператор | Человек с доступом к серверу. Через CLI создаёт и блокирует пользователей, сбрасывает пароли, выпускает и отзывает ключи |
| Пользователь | Управляет своими событиями, задачами и досками, видит чужую занятость |
| Участник события | Видит все детали события, меняет его и состав участников, может удалить его у всех или выйти из него |
| Участник доски | Права зависят от роли на доске: owner, editor или viewer |
| Интеграция | Вызывает API в пределах scopes ключа и прав пользователя, которому этот ключ принадлежит |

## 3. Основные сценарии

- **Первый вход.** Оператор создаёт пользователя, CLI выводит одноразовый пароль, пользователь входит и задаёт свой пароль.
- **Совместное событие.** Пользователь создаёт событие и выбирает участников. Событие сразу появляется у них в календаре вместе с уведомлением. Любой участник может его изменить, остальные получат уведомление.
- **Подбор времени.** При создании события пользователь видит интервалы занятости выбранных людей и выбирает время, не видя чужих деталей.
- **Задача.** Создание карточки, установка срока, приоритета и исполнителя, отображение в списке и календаре, закрытие.
- **Совместный список.** Создание доски «Покупки», добавление участника, совместная работа с карточками с автоматическим обновлением.
- **Kanban.** Пользователь настраивает колонки доски и перетаскивает карточки между ними. Идентификатор задачи не меняется, а календарь показывает её срок независимо от колонки.

## 4. Приватность

Личное событие видят только его участники. Остальные пользователи видят лишь интервал «занят» без названия, описания, места и списка участников. Доступ к доске не даёт доступа к личному календарю её участников.

## 5. Календарь

### 5.1 Представления

- Месяц, неделя, день. На мобильном — компактный месяц и список событий выбранного дня.
- Переключение периода, переход к сегодняшнему дню, поиск, цвета категорий, фильтр по типам элементов.
- Показ событий и сроков задач. Слой задач можно отключить.
- Корректный показ пересекающихся и многодневных событий и событий на весь день.

### 5.2 Поля события

| Поле | Требование |
|---|---|
| Название | Обязательно |
| Время | Начало и конец либо признак «весь день». Интервал проверяется на корректность |
| Описание, место | Необязательны |
| Категория | Личное, работа, учёба или своя. Определяет цвет и фильтры, на доступ не влияет. У каждого участника своя |
| Участники | Выбираются из существующих пользователей |
| Повторение | Нет, каждый день, каждую неделю, каждый месяц |
| Напоминания | Время до начала. Можно обойтись без напоминания. У каждого участника свои |

### 5.3 Совместные события

- Статусов ответа нет: добавленный участник сразу видит событие в своём календаре.
- Все участники равноправны. Каждый может менять поля события, добавлять и убирать участников, удалять событие у всех.
- Участник может выйти из события, не затрагивая остальных. Если участников не осталось, событие удаляется.
- Пересечение по времени не запрещает создание события, интерфейс лишь предупреждает о нём.
- Удаление мягкое, данные остаются в базе.

### 5.4 Серии

- Серия бывает бесконечной либо ограниченной датой или числом повторов.
- В месяце без нужного числа повтор пропускается. Серия «каждый месяц 31-го» даёт 31 января, 31 марта, 31 мая и так далее.
- В MVP серия меняется и удаляется только целиком. Исключения и правка одного экземпляра появятся в v1.1.

### 5.5 Напоминания

Напоминание срабатывает за заданное время до начала каждого экземпляра события и создаёт уведомление внутри сайта. Оно не теряется при простое сервера: после запуска пропущенные напоминания появятся в центре уведомлений без дублей.

### 5.6 Занятость

- Любой пользователь может запросить занятость другого за период.
- Ответ содержит только интервалы времени. Соседние и пересекающиеся интервалы склеиваются, чтобы нельзя было посчитать чужие события.
- Занятость формируют только события со временем. События на весь день и задачи её не формируют.

## 6. Задачи, списки и доски

### 6.1 Модель

Все задачи хранятся как карточки досок. Список, Kanban и календарь показывают одни и те же данные, поэтому смена вида не меняет ни карточки, ни их порядок.

### 6.2 Поведение

- Пользователь создаёт личную или совместную доску и добавляет участников с нужной ролью.
- Новая доска получает колонки «К выполнению» и «Готово» и выбранный вид по умолчанию: список или Kanban.
- У каждого пользователя есть личная доска по умолчанию.
- Карточка содержит описание, приоритет P1–P4, исполнителей, метки, дату начала, дедлайн, чек-лист, напоминание, комментарии и историю и может быть связана с событием.
- Исполнителем может быть только участник доски.
- Завершение задачи переносит её в завершающую колонку. Выполненные карточки доступны в фильтрах.
- Статус задачи определяется колонкой, а не булевым признаком «выполнено».
- Карточку можно перенести на другую доску. Метки при этом сбрасываются, а исполнители, которых нет на новой доске, снимаются.

### 6.3 Kanban и колонки

- Колонки можно создавать, переименовывать, менять местами, удалять и отмечать как завершающие.
- Карточки перетаскиваются внутри колонки и между колонками, на компьютере и на телефоне. Колонки тоже перетаскиваются.
- Каждое перетаскивание дублируется действием «Переместить в…» и управлением с клавиатуры.
- Перенос атомарный. При одновременных переносах все пользователи приходят к одному порядку.
- Перенос в завершающую колонку отмечает задачу выполненной, перенос из неё снимает отметку.
- Смена признака завершающей колонки меняет статус всех её карточек.
- Колонку с карточками можно удалить, только выбрав колонку для их переноса.
- На доске всегда есть хотя бы одна завершающая и одна незавершающая колонка.
- Доска фильтруется по исполнителю и метке.

### 6.4 Метки, комментарии, история

- **Метки** задаются на доске: название и цвет. У карточки их может быть несколько.
- **Комментарии** — простой текст, без вложений и упоминаний. Автор может изменить или удалить свой комментарий, owner может удалить любой. Уведомление получают исполнители и те, кто уже комментировал карточку.
- **История** показывает, кто и когда создал карточку, изменил поля, перенёс её, закрыл, сменил исполнителей, метки, чек-лист и связи. Её видят все участники доски.
- Перестановки внутри колонки в историю не попадают. История не редактируется.

### 6.5 Права на доске

| Действие | viewer | editor | owner |
|---|---|---|---|
| Читать доску, карточки, комментарии и историю | да | да | да |
| Создавать, менять, переносить, закрывать и удалять карточки | нет | да | да |
| Менять исполнителей, метки карточек и чек-листы | нет | да | да |
| Писать комментарии | нет | да | да |
| Управлять колонками и метками доски | нет | да | да |
| Менять название, описание и вид доски | нет | нет | да |
| Управлять участниками | нет | нет | да |
| Архивировать доску | нет | нет | да |

На доске всегда есть хотя бы один owner.

### 6.6 Задачи в календаре

- Задача без срока показывается в списке, но не в календаре.
- Задача со сроком показывается на дату дедлайна независимо от колонки. Выполненная задача отображается как выполненная.
- Исполнители видят задачу в своём календаре. Задачу без исполнителя видят все участники доски.
- Вид «Календарь» на доске показывает все её задачи со сроком независимо от исполнителя.
- Задача не формирует занятость. Время работы над ней планируется отдельным связанным событием.

## 7. Уведомления и синхронизация

Уведомления живут внутри сайта: они хранятся на сервере и видны в центре уведомлений при входе.

| Объект | Поводы |
|---|---|
| Событие | Добавление в событие, изменение времени, места или названия, удаление, исключение из участников, напоминание |
| Задача | Назначение, изменение существенных полей, новый комментарий, наступление срока, напоминание |
| Доска | Добавление на доску |

Пользователь не получает уведомлений о собственных действиях. Уведомление о сроке получают исполнители карточки, а если их нет, владельцы доски.

Открытые вкладки получают изменения без перезагрузки, целевая задержка не больше 10 секунд. Сервер остаётся источником истины, а оптимистичное обновление в интерфейсе должно корректно обрабатывать конфликты.

## 8. Интеграции

- Ключ выдаётся оператором, показывается один раз и передаётся в заголовке `Authorization: Bearer`.
- Ключ может не иметь срока действия, но всегда отзывается вручную.
- Права ограничены scopes и правами пользователя-владельца.
- Два активных ключа могут работать одновременно, что позволяет заменить ключ без простоя.
- API доступен только из локальной сети.

Сама интеграция Ады делается в отдельном проекте, Planny только предоставляет API.

## 9. Нефункциональные требования

| Критерий | Требование |
|---|---|
| Клиенты | Современные браузеры на компьютере и телефоне, без горизонтального скролла основных экранов |
| Скорость | Обычные CRUD-операции в локальной сети: p95 меньше 500 мс |
| Данные | Серверная пагинация, календарные выборки только по диапазону |
| Устойчивость | Перезапуск компонентов не теряет данные пользователя |
| Логи | Структурированные логи с `request_id`, без токенов, паролей и личного содержимого |
| Резервирование | Регулярная копия PostgreSQL и проверенная процедура восстановления |
| Безопасность | Пароли в Argon2id, защита от CSRF, лимит неудачных входов, аудит действий оператора |
| Тесты | Unit для доменной логики, integration для CRUD и прав, e2e для основных сценариев |

## 10. Вне MVP

- **v1.1:** исключения в сериях, сложные повторения, настройки уведомлений, перетаскивание событий в календаре.
- **v1.2 и дальше:** интеграция Ады, автоматизации, внешние календари, поиск свободного слота, вложения, таблица как вид доски, сложные фильтры.
- **Когда понадобится:** браузерные push-уведомления и PWA, двухфакторный вход, SSE вместо опроса.

## 11. Критерии приёмки

| № | Сценарий |
|---|---|
| AC-01 | Пользователь вне локальной сети входит на сайт по HTTPS и работает с календарём. Адрес и порт API снаружи недоступны |
| AC-02 | Неавторизованный запрос к API отклоняется даже из LAN. Ключ с недостаточным scope не может менять события и задачи |
| AC-03 | Самостоятельная регистрация невозможна. Оператор создаёт аккаунт через CLI на сервере, сетевого маршрута для этого не существует |
| AC-04 | Пользователь А создаёт событие и добавляет Б. Событие сразу появляется у Б вместе с уведомлением. Б меняет событие, А видит изменение и получает уведомление. Любой из них может удалить событие у обоих |
| AC-05 | Б видит занятость А только как интервалы, без деталей. События на весь день и задачи занятость не формируют |
| AC-06 | Два участника общей доски меняют карточки и видят согласованное состояние. Срок задачи отражён в календаре |
| AC-07 | Ключ интеграции работает после перезапуска приложения, а после отзыва сразу перестаёт работать |
| AC-08 | Серия «1-го числа в 01:00» показывается в каждом месяце. Серия «31-го» пропускает короткие месяцы. Бесконечная серия показывается в любом запрошенном периоде |
| AC-09 | Событие на весь день показывается в один и тот же календарный день у пользователей с разными часовыми поясами |
| AC-10 | Напоминания, наступившие во время простоя worker, появляются после его запуска без дублей |
| AC-11 | Резервная копия восстанавливается на чистой базе по описанной процедуре |
| AC-12 | Изменение одного пользователя появляется в открытой вкладке другого не позже чем через 10 секунд без перезагрузки |
| AC-13 | Карточку перетаскивают между колонками мышью, касанием и с клавиатуры. Идентификатор и положение сохраняются после перезагрузки, другой пользователь видит перенос в пределах 10 секунд |
| AC-14 | Два пользователя одновременно переносят карточки в одно место колонки. Оба приходят к одному порядку, ошибок и дублей нет |
| AC-15 | Колонку с карточками нельзя удалить без выбора колонки для переноса. Нельзя удалить последнюю завершающую или незавершающую колонку |
| AC-16 | История карточки показывает автора и время создания, изменения полей, переноса и смены исполнителей. Переименование колонки не портит старые записи |
| AC-17 | Editor пишет комментарий, исполнители получают уведомление. Viewer читает комментарии и историю, но не может писать и переносить карточки |
