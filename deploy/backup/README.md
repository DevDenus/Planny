# Резервные копии

Копия — это дамп базы PostgreSQL, который `pg_dump` снимает внутри контейнера `db`. На хосте ничего дополнительно ставить не нужно, а останавливать стек для копии не надо.

## Что входит в копию

Вся база `planny`: пользователи с хешами паролей, доски, задачи, события и таблица миграций. Файлов вне базы в MVP нет. В копию не входит `deploy/.env` с секретами, его храните отдельно.

Копии содержат хеши паролей и личные данные. Храните их с ограниченным доступом: копии создаются с правами `600`, а папку с копиями держите доступной только владельцу. Папка `deploy/backup/dumps/` закрыта `.gitignore`, но при копировании на другой диск ограничения доступа сохраняйте.

## Как сделать копию

Скрипты работают из любой папки.

```bash
deploy/backup/backup.sh
deploy/backup/backup.sh /mnt/backup/planny
```

Файл `planny-ГГГГММДД-ЧЧММСС.dump` (время UTC) попадает в `deploy/backup/dumps/`, если не указана другая папка. Сначала он пишется под временным именем `.tmp`, проверяется и только потом получает итоговое имя. После успешной копии удаляются файлы `planny-*.dump` старше `BACKUP_KEEP_DAYS` дней.

Эта проверка читает только оглавление архива и не замечает повреждений дальше по файлу. Убедиться, что копия восстановится, можно только восстановлением, см. [пробное восстановление](#пробное-восстановление).

## Как восстановить

```bash
deploy/backup/restore.sh deploy/backup/dumps/planny-20261104-120000.dump
```

Скрипт работает так, что повреждённая копия не может испортить текущие данные:

1. Полностью разворачивает копию в отдельную базу `planny_restore`. Сервисы в это время работают. Если файл повреждён, скрипт останавливается, а текущая база остаётся нетронутой.
2. Показывает, сколько пользователей в копии, и просит ввести `restore`. Флаг `--yes` пропускает вопрос.
3. Останавливает `api`, `worker` и `bff` и одним действием подменяет базу. Прежняя база остаётся под именем `planny_replaced`.
4. Запускает сервисы. Миграции выполняются сами, поэтому копия, снятая на старой версии кода, поднимется без ручных действий.
5. Если сервисы не запустились, возвращает прежнюю базу и запускает их на ней. Если запустились, удаляет прежнюю базу.

На время восстановления на диске нужно место ещё на одну копию базы.

На чистой базе, например в новом стеке с пустым томом `db-data`, запускайте `restore.sh` так же: скрипт сам поднимет `db`.

Если скрипт прервали на шаге подмены, `api`, `worker` и `bff` могут остаться остановленными, и достаточно запустить `restore.sh` снова. Если он отказывается работать из-за оставшейся базы `planny_replaced`, значит, прошлый запуск оборвался сразу после подмены. Проверьте работу приложения и удалите эту базу вручную.

## Как проверить

Весь путь проверяется одной командой на отдельном стеке, данные разработки она не трогает:

```bash
make restore-check
```

Она подсовывает `restore.sh` обрезанную, зашумлённую, пустую и чужую копии, убеждается, что база не изменилась, а затем восстанавливает настоящую копию на работающей и на чистой базе и входит старым паролем.

После восстановления настоящей копии сверьте пользователей вручную:

```bash
docker compose --project-directory deploy -f deploy/compose.yaml -f deploy/compose.dev.yaml exec api planny users list
```

Список должен совпасть с пользователями до копии. Затем войдите в приложение под одним из этих логинов и старым паролем. На сервере вместо `compose.dev.yaml` используйте `compose.prod.yaml`.

## Пробное восстановление

`backup.sh` проверяет только оглавление архива, поэтому настоящую гарантию даёт лишь восстановление. `trial-restore.sh` делает его целиком, но не на живой базе, а в отдельном временном проекте `planny-trial`:

```bash
deploy/backup/trial-restore.sh
deploy/backup/trial-restore.sh /mnt/hdd2/planny-backups/planny-20261104-033000.dump
```

Без аргумента скрипт берёт самую новую копию `planny-*.dump` из `BACKUP_DIR`. Он:

1. Поднимает пустую базу `planny` в проекте `planny-trial`, без портов и без сети `edge`. Имя проекта зашито в скрипте, переменная `COMPOSE_PROJECT_NAME` на него не влияет, поэтому живой проект и его том скрипт не трогает.
2. Разворачивает копию целиком через `pg_restore`.
3. Выполняет `alembic upgrade head` текущей версии поверх восстановленных данных, затем `alembic check`.
4. Читает пользователей через ORM командой `planny users list` и сверяет их число с таблицей `app_user`.
5. Печатает файл, размер, возраст, число пользователей и ревизию Alembic, после чего удаляет временный проект вместе с томом. Остатки прерванного запуска он удаляет в начале.

Код выхода 0 означает, что всё прошло. Если самой свежей копии больше `TRIAL_MAX_AGE_HOURS` часов (по умолчанию 48), скрипт всё равно выполняет восстановление, а в конце завершается с ошибкой: таймер `planny-backup`, похоже, не работает. Для копии, указанной аргументом, возраст не проверяется.

На машине разработки то же самое делает `make trial-restore`. Образы и пароль берутся из `deploy/.env`, на сервере это образы и пароль текущей версии.

## Расписание на сервере

Два таймера systemd запускают скрипты из `$PLANNY_ROOT/current/deploy/backup/`. Юниты лежат в `deploy/server/systemd/`, `deploy/server/update.sh` копирует их в `/etc/systemd/system/` и подставляет вместо `@PLANNY_ROOT@` настоящий корень, по умолчанию `/opt/planny`.

| Таймер | Когда | Что запускает |
|---|---|---|
| `planny-backup.timer` | каждый день в 03:30 по местному времени, со сдвигом до 10 минут | `backup.sh` |
| `planny-trial-restore.timer` | по воскресеньям в 04:30 | `trial-restore.sh` |

Обе службы читают `$PLANNY_ROOT/.env` и запускаются с `PLANNY_ENV=prod`. У таймеров стоит `Persistent=true`: если сервер в это время был выключен, пропущенный запуск выполнится при следующей загрузке. Пробное восстановление стартует после копии, если они совпали по времени.

```bash
systemctl list-timers 'planny-*'
systemctl --failed
sudo systemctl start planny-backup.service
sudo systemctl start planny-trial-restore.service
journalctl -u planny-backup -e
journalctl -u planny-trial-restore -e
```

Упавший запуск виден в `systemctl --failed`, причина в `journalctl`. Проверяйте этот список после каждого воскресенья: никакого другого уведомления нет. Ручной запуск `sudo systemctl start planny-trial-restore.service` ждёт окончания и возвращает код выхода службы.

## Второй диск

Копии на сервере должны лежать на втором диске, а не на системном. Для этого в `.env` задаются:

- `BACKUP_DIR=/mnt/hdd2/planny-backups` — папка для копий.
- `BACKUP_MOUNT=/mnt/hdd2` — точка монтирования второго диска.

Если `BACKUP_MOUNT` задана, `backup.sh` перед любым действием проверяет, что это точка монтирования и что папка копий лежит внутри неё. Иначе он завершается с ошибкой и ничего не создаёт: без этой проверки `mkdir` на размонтированном пути молча заполнил бы системный диск. Служба в этом случае падает и видна в `systemctl --failed`.

## Переменные

- `PLANNY_ENV` — `dev` или `prod`, выбирает файл `compose.<значение>.yaml`. По умолчанию `dev`. `trial-restore.sh` его не использует.
- `BACKUP_DIR` — папка для копий. По умолчанию `deploy/backup/dumps`. Аргумент `backup.sh` важнее этой переменной. `trial-restore.sh` ищет в ней самую новую копию.
- `BACKUP_KEEP_DAYS` — сколько дней хранить копии. По умолчанию 14.
- `BACKUP_MOUNT` — точка монтирования второго диска. Если задана, `backup.sh` пишет только внутрь неё. По умолчанию не задана.
- `TRIAL_MAX_AGE_HOURS` — какого возраста может быть самая свежая копия для `trial-restore.sh`. По умолчанию 48.

```bash
PLANNY_ENV=prod BACKUP_DIR=/mnt/hdd2/planny-backups BACKUP_MOUNT=/mnt/hdd2 deploy/backup/backup.sh
```
